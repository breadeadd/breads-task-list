# Data Model and State Structure

## Overview

Understanding the shape of your data is the foundation for understanding everything else in this app. State is split between two components:

- **`App.jsx`** owns auth, theme, pages list, active page, and the session-wide completed list.
- **`Page.jsx`** owns all todo and list state scoped to the active page.

The primary source of truth is Supabase. React state is a local cache of the database.

---

## Core Object Shapes

All objects in state come directly from Supabase rows. IDs are UUIDs (strings like `"a1b2c3d4-..."`), auto-generated by Postgres.

### Todo Object

```js
{
  id: "a1b2c3d4-...",       // UUID, generated by Supabase
  user_id: "f4e3d2c1-...",  // which user owns this
  page_id: "b2c3d4e5-...",  // which page it belongs to
  list_id: null,             // null = root inbox; a UUID = inside a named list
  text: "Buy groceries",
  is_completed: false,
  position: 0,               // display order within its container
  created_at: "2024-..."
}
```

### List Object (in React state)

Lists in Supabase have no nested todos — that nesting is added in memory when data loads. In React state, a list carries a `todos` array hydrated from the todos table:

```js
{
  id: "c3d4e5f6-...",
  user_id: "f4e3d2c1-...",
  page_id: "b2c3d4e5-...",
  title: "Uni Work",
  position: 1,
  created_at: "2024-...",
  todos: [                   // ← added in memory, not a Supabase column
    { id: "...", text: "Read chapter 4", ... },
    { id: "...", text: "Submit essay", ... }
  ]
}
```

### Page Object

```js
{
  id: "b2c3d4e5-...",
  user_id: "f4e3d2c1-...",
  title: "My Page",
  position: 0,
  created_at: "2024-..."
}
```

## The Two-Tier Todo Structure

The app has two places where todos can live:

```
Page state
├── todos[]          ← Root inbox (active tasks at the top)
└── lists[]
    ├── list { id, title, todos[] }   ← e.g. "Uni Work"
    └── list { id, title, todos[] }   ← e.g. "Work"
```

In Supabase they are all rows in the `todos` table. The distinction is `list_id`:

- `list_id = null` → root inbox todo
- `list_id = <uuid>` → todo belongs to that named list

When data loads in `Page.jsx`, todos are split and hydrated into these two structures:

```js
const rootTodos = todosData.filter(t => !t.list_id && !t.is_completed)
const hydratedLists = listsData.map(list => ({
  ...list,
  todos: todosData.filter(t => t.list_id === list.id && !t.is_completed)
}))
```

## Immutable State Updates

React requires you to **never directly mutate state**. Instead, always create a new copy with your change applied.

### Wrong (mutation):
```js
todos[0].text = "New text"  // React won't notice this change
setTodos(todos)
```

### Correct (immutable copy):
```js
const updated = todos.map((todo, i) =>
  i === 0 ? { ...todo, text: "New text" } : todo
)
setTodos(updated)
```

### Three levels deep

Updating a todo inside a list requires replacing the todo, then replacing the list, then replacing the lists array:

```js
const updatedLists = lists.map((list) =>
  list.id === listId
    ? { ...list, todos: list.todos.filter((_, i) => i !== index) }
    : list
)
setLists(updatedLists)
```

## State Slices Reference

### `App.jsx` state

| Variable | Type | Purpose |
|---|---|---|
| `user` | `object \| null` | The Supabase auth user object |
| `authLoading` | `boolean` | True while the initial auth session check is in progress |
| `pages` | `Array<page>` | All of the user's pages |
| `activePage` | `page \| null` | The currently selected page |
| `pendingRenamePageId` | `uuid \| null` | Triggers auto-edit rename on the matching `PageTab` |
| `completed` | `Array<todo>` | Tasks completed this session, across all pages |
| `theme` | `'dark' \| 'light'` | Current visual mode (stored in `localStorage`) |

### `Page.jsx` state (scoped to one page)

| Variable | Type | Purpose |
|---|---|---|
| `todos` | `Array<todo>` | Active tasks in the root inbox for this page |
| `lists` | `Array<list>` | Named list sections with their nested todos, for this page |
| `todoValue` | `string` | Live text in the task input field |
| `activeListId` | `uuid \| null` | Which list section is currently selected |
| `editingFromListId` | `uuid \| null` | Tracks if the input is targeting a specific list |
| `pendingRenameListId` | `uuid \| null` | Triggers auto-focus rename on new lists |
| `activeDragId` | `uuid \| string \| null` | ID of the item currently being dragged |
| `activeDragType` | `'todo-item' \| 'list-section' \| null` | Category of the active drag |

## Persistence

### Source of truth

Supabase is the primary source of truth for all todos, lists, and pages. React state is a local in-memory cache.

**Write pattern:** state updates happen immediately (optimistic update), then the Supabase write happens in the background. If the write fails, an error is logged but state is not rolled back.

### What still uses localStorage

Only `theme` is stored in `localStorage`:

```js
localStorage.setItem('theme', theme)
```

Everything else (todos, lists, pages, completed) lives in Supabase.

---

## Session vs. Persistent Data

| Data | Persists to Supabase? | Notes |
|---|---|---|
| `todos` | Yes | Written on every add, delete, complete, or reorder |
| `lists` | Yes | Written on every add, delete, rename, or reorder |
| `completed` | Yes | Written on complete; deleted on undo or session reset |
| `pages` | Yes | Written on add, rename, or delete |
| `theme` | No (localStorage only) | Not synced across devices |
| `todoValue` | No | In-memory only, just the current input string |
| `activeListId` | No | Rehydrated from first list on page load |
| UI state (drag, rename) | No | Transient interaction state |

`completed` is intentionally designed to feel "session-like" (reset button, session counter) but it does persist across refreshes — you don't lose completed items on a reload.
